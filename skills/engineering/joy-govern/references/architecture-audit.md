# 架构摩擦体检

用于用户要求检查长期代码结构、职责分散、难理解/难测试或模块改造候选时。默认只读，先确定覆盖范围、近期变化热点、实际调用/状态边界、glossary/ADR、现有保护和代码负责人。

候选依据是现实摩擦：同一规则散落、调用方反复拼装内部细节、状态有多个所有者、难以穿过真实故障路径测试、一个修改波及大量位置。仅有小文件、薄转发或“看着不优雅”不构成改造价值。接口/深度判断按名称交 joy-shape 的模块设计分支，领域专业架构仍由当前主导 Skill 承接。

## 候选产物

每项保留源文件/调用证据、当前问题、before/after 的职责变化、依赖类别、caller/测试影响、成本、风险、保护与恢复、建议强度及未知项。before 是源码事实，after 是拟议设计，必须明显区分。已有 ADR 冲突只有现实证据足以重新讨论时才列，不自动废弃决定。

优先列少量有依据的候选与推荐，或明确“当前范围无改造价值”；不按固定数量凑出全仓重构。先问哪个问题值得解决，再设计接口，不自动改代码、删测试或建立任务票。

用户需要可视化 HTML 报告时，视觉与构图按名称交 joyally-design，图表产物交 joyally-image，从同一源码证据做 before/after。保留可读文件、来源、宽窄屏/键盘/打印结果；不默认联网 CDN，不把静态图冒充运行系统。没有可视化工具时明确只交文本，不声称与请求等价。

选中后由 joy-shape 收敛接口、状态所有权、替代设计、场景和验收，必要时做原型；写入/实现/提交各沿当前授权。治理阶段不接管 Build/Review/Loop，不另造分支或 worktree 台账。
