# JoyStack · Debug

跨技能交接按名称使用当前宿主已发现的 Skill，不要求相邻安装目录；缺少所需能力时报告缺项，不猜路径或擅自安装。

先建立可重复的失败事实：期望与实际、最小条件、频率、环境和可观察证据。然后把问题缩小到具体边界，为每个假设设计一个能推翻它的观察或实验。

难复现、间歇性或性能故障读取[可运行诊断](references/diagnosis-loop.md)，固定已执行的红灯反馈、区分实验、原场景回验与资源清理；没有可运行证据时保留假设，不用源码猜测宣称修复成功。

原因不明时先保持产品行为不变，只增加可回收的诊断观察或失败用例；能测试复现就先确认它确实失败，不能本地复现则明确依赖的日志、环境和结论把握。以前正常的问题优先缩小引入变更，错误值沿数据边界反向追踪，有正常对照时做受控差异实验。

根因只有同时满足两点才成立：能从触发条件沿具体代码或状态边界解释到用户现象，并能解释所有已观察差异。修在坏状态第一次产生的位置，不用无依据的重试、sleep、吞错、扩大超时或输入特判遮住症状。

不要把偶然消失、一次重试成功或日志里最醒目的错误当作根因。先修导致失效的机制，再用最贴近根因的回归保护确认；如果只能降低概率，要如实说明残余条件与监控/恢复路径。

修复后再问这是单点遗漏还是可重复的错误模式。只有后者才全仓扫描同类位置，并根据证据提议静态检查、测试门禁或审查重点；常驻规则的写入仍服从项目授权。连续多个假设被推翻、两轮修复仍不收敛或证据互相矛盾时，停止堆补丁，整理已确认事实、已排除假设和最小复现，再请求独立会诊或用户决定。

需要把复现转为回归测试、诊断测试本身错误或处理不稳定测试时，交给 joy-test 取得能穿过真实失败机制的测试证据；产品根因与修复仍由本模块主导，缺少正确测试 seam 时明确保护缺口，不编造测试通过。

当根因表明需求或系统边界本身有误，回到 `joy-shape`；修复完成后交给 `joy-verify`。共享交接标准见套件契约（按技能名发现 `joy-stack`，再从其实际目录读取 `references/stack-contract.md`）。
