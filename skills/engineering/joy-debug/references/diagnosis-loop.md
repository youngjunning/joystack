# 可运行诊断与收尾

用于难复现缺陷、间歇性失败和性能回退。输出是用户原始症状的反馈、排除证据、因果解释、回归与原场景回验。读源码可以定位运行入口，不能只凭相似代码宣称根因。

## 先建立反馈

写清期望、实际、触发输入/顺序、环境与 revision；选择能穿过失败代码路径并断言原始症状的最小入口。记录一个已实际运行的命令、输入/环境标识和脱敏结果，使修复前能变红、修复后能转绿。启动异常、导入失败、“没有崩溃”不是目标缺陷的有效反馈。

按故障边界选择手段，而非全部尝试：规则/接口用定向测试，协议用最小 HTTP/CLI 请求，时序用受控重放与并发压力，回退用已知好坏版本对照或隔离 bisect，输入域用预算固定的 fuzz/差分，进程/资源用 debugger、profiler、查询计划或轨迹。HITL 只有在 Agent 确实不能执行时使用，给真人明确步骤和回传字段，不索取凭据、不驱动未授权设备。

让反馈尽量快、确定且能辨别假设：固定 seed、时钟、依赖/数据版本和隔离资源；优化初始化但不删负载机制。间歇性故障先记录原触发次数与失败率，设计有界重复/压力实验并报告分母；不临时无限重跑、不用人为 sleep 改产品结果。

无法建立反馈时列已尝试入口、环境/资料/授权缺口，结论保持待验证。可继续有依据的源码分析和只读取证，但不能跳到“已定位”或“修复验证通过”；线上仪器注入、写请求和环境更改各自需要授权。

## 缩小并证伪

1. 确认反馈观察的是用户原始症状，不是附近的新错误。逐项减少输入、调用者、配置、步骤，减一次复跑一次；保留所有仍影响失败的条件，不丢多调用者或真实依赖特征。
2. 多个解释仍成立时列少量按证据排序的竞争假设，每项有能推翻它的预测与实验；不因第一个说得通就开始补丁。已有决定性证据时不为凑固定个数造假设。实验前公开判断与理由，领域信息可调整次序。
3. 一次改变一个区分条件，记录版本、观测结果、支持/反驳和未解差异。性能问题先用同口径基线和 profiler 找退化，不拿日志量或主观“更快”代替测量。
4. 需要临时日志时在能区分假设的边界加标记，记录本任务新增的文件、日志前缀、计时器、临时状态与配置差异。不要“全量打印再 grep”，避免敏感数据。

根因必须解释完整因果链和所有已观察差异。连续失败后检查共同前提与诊断手段本身，不因重复失败自动提高预算；无法收敛时保留最小复现、排除项和具体下一步。

## 修复、回归、清理

在正确 seam 上把失败变为回归保护，测试须覆盖真实调用模式；浅层测试无法复现故障时由 joy-test 明示缺口，不凑绿灯。修在坏状态最早产生的位置，不靠吞错、无依据重试或扩大超时遮盖。

完成前分别取得：回归测试红/绿或不能取得的原因，相关测试，原始完整场景回验，以及适用的性能对照。最小样例通过不替代原始负载、实际设备或部署目标；不能运行的边界继续标为未验收。

按本任务清单清理临时 instrumentation、timer、进程、端口、配置和实验文件，核对源码 diff。仅移除自己新增且用途已确认的内容，保留用户/并行修改和必要现场；诊断命令、假设结论、回归与恢复入口留可追溯位置。清理失败不要覆盖首因，未恢复的资源必须单列。

已获产品修复授权才修改产品。测试本身的故障交 joy-test，整体验收交 joy-verify，原 Loop 继续掌管复查；本参考不另造诊断 runner、无限循环或发布权限。
