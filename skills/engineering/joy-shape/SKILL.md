# JoyStack · Shape

跨技能交接按名称使用当前宿主已发现的 Skill，不要求相邻安装目录；缺少所需能力时报告缺项，不猜路径或擅自安装。

把“想做什么”变成一个足够实施的任务契约：目标用户或使用场景、可观察结果、明确不做的范围、已有约束、失败与恢复边界，以及验收证据。

让契约的重量匹配任务：明确、低风险的单模块改动用几句话直接对齐；常规功能在对话中讲清外部变化、范围、取舍与验证；跨系统、数据格式、发布链路或高风险改造才写入项目既有的规格位置。不要用评分表或长模板制造“就绪”的假象。

方案提到的现有路径、复用基建和验证命令必须先在仓库核实。实现交接至少写清允许改动与禁改范围、必须复用的边界、局部快检、收尾门禁，以及哪些产品或兼容取舍仍需决定。审方案看事实与边界；审已写出的代码交给 `joy-review`，不要混为一次泛化评审。

优先使用当前对话、仓库约定和实际代码补全上下文；只在缺失的选择会改变结果、成本、数据兼容性、外部影响或不可逆性时提问。不要把 Agent 提议伪装成用户决定，也不要为了消除所有不确定性而阻塞小改动。

跨模块、权限、付费、数据迁移、外部发布或目标环境验收无法本地证明时，明确它们的所有者和停止条件。契约清楚后交给 `joy-build`；需要验证策略时同时交给 `joy-verify`。共享交接标准见套件契约（按技能名发现 `joy-stack`，再从其实际目录读取 `references/stack-contract.md`）。
