# 模块深度、接口与 seam

用于接口难用、职责分散、实现细节泄漏、替换依赖困难或需要比较设计方案时。先读真实 caller、变化热点、测试和依赖；按项目术语沟通，不强迫把 service/component/API 都改成一套上游词汇。

## 判断而非指标

模块是具有调用约定和实现的职责单元，可以是函数、包或跨层切片。接口包含类型以外的必知条件：顺序、状态不变量、错误、配置、权限和性能。深度看 caller 学习这些条件后得到多少可观察能力；实现很长、方法很少都不能单独证明“深”。

seam 是能更换行为的接合位置，adapter 是满足该约定的具体实现。外部 seam 面向 caller，内部 seam 只服务实现隔离和自身测试；不能为测试方便把内部协作者都变成公开接口。领域边界也不是一见 I/O 就新增的 port。

核对三件事：调用者是否反复做同样准备/补救，维护一个规则是否要同时修很多位置，删掉某层后复杂度是集中消失还是转嫁给更多 caller。只有能减少真实泄漏和维护负担才是重构收益。隔离、身份、兼容、观测等薄层可能有真实契约，不因转发少就删。

## 依赖与测试策略

| 边界 | 设计与保护方式 |
| --- | --- |
| 进程内 | 把相同职责集中，通过行为接口测试；只有确实需要隔离时才做 adapter |
| 可替代的本地状态/I/O | 优先用已有本地替身或测试实例，验证其与真实目标差异，不能由替身通过外推生产 |
| 自有远端 | 逻辑所有者与 transport 明确，必要时注入 port/adapter；跨进程协议仍单独验收 |
| 真正第三方 | 依赖可替换时按外部契约注入，测试可用 mock/replay；真实鉴权、错误和服务行为仍保留待验边界 |

至少一个有现实理由的替换场景才引入 seam。生产/测试两个 adapter 是可检查的证据，不是强制“凑两个”或拒绝未来有价值的隔离。复用项目现有接口和资源生命周期，不搭重复抽象。

## 比较形状

先说明约束、caller 样例、需隐藏的复杂度、状态所有权和依赖。必要时写两个真正不同的方案：从常见调用简便性、扩展需求或隔离位置作不同取舍；每个包含使用示例、不变量、错误、adapter、维护成本和明确放弃项。差异不是只改类名。

不自动并行调用多个模型；只有用户或环境明确允许 delegation 时才分派互不重复的视角，不能把阅读上游方法当作授权。没有并行能力也能在本任务依次比较，说明证据而非模型评分。

建议应说明哪一个适合当前需求，哪些结论来自假设，是否有更小的原路径调整。重大产品/架构选择继续交当前架构 Skill，不把这个参考升级为第二个总控。

## 安全实现

把兼容承诺、状态唯一所有者、生命周期、调用方迁移和验收交给 joy-build。删除测试前必须由 joy-test 核对每项保护目标是否消失、是否已有等效的新证据；内部测试仍保护独特错误机制时保留，不能因为“深模块”就批量移除。

前端使用该分支可判断职责、状态和可测试边界，但不得借接口最小化删减用户要求的视觉、交互、状态、动效或可访问性；视觉原型按 joy-shape 的原型分支转交设计专业能力。
