# 用原型回答一个问题

用于无法仅靠讨论确认的状态模型、业务逻辑或 UI 取舍。输入是明确问题、需要的逼真程度与禁止副作用；输出是可操作产物、实际观察、已证实选择和仍不成立的假设。不是省去生产实现门禁的捷径。

## 分支与停止条件

先写下问题、场景、预期可观察差异与完成条件。逻辑问题围绕状态/行为；UI 问题围绕页面目的、内容密度、信息层级和交互。两者都涉及时分别验收，不拿漂亮页面证明状态模型正确。问题足够明确就实施；目标不同才澄清，不按目录名盲选。

在项目允许位置标明 prototype 与测试环境；已有页面有承载位置时复用其 shell 和只读数据流。不要新增与现有路由/权限不相容的顶层架构。启动方式必须单一可复现，产物可打开；优先现有工具，独立 HTML 合适时使用但不强制全部原型变 HTML。

默认只用内存、stub 或获准的隔离数据；不写真实交易、发信、发布、持久配置或用户数据。问题涉及持久化才单独核对 scratch 存储、恢复与清理授权。原型标记不等于数据隔离。

## 逻辑分支

把被验证的 reducer、状态机或转换函数与 DOM 展示分开。提供清楚的当前状态、可操作动作、重置与步骤式场景；覆盖正常、真实边界和非法动作，展示约束拒绝而非悄悄丢弃。每步实际调用模型并刷新可读状态，不能用静态动画冒充执行。

面向领域读者使用业务词，不要求他们读 JSON。能改变后续判断的状态都应可见；引导场景从已知初始状态开始，记录运行结果而非仅保存截图。实现代码如果要用于产品，仍重新确认边界并补测试，不直接晋升为可信生产代码。

## UI 分支

按名称交给 joyally-design 主导视觉方案；需要主题、图像或动效时由相应专业 Skill 接手，本分支拥有问题和取舍记录，不自行发明另一套视觉默认。若专业能力不可用，只完成已有工具能验证的部分并明确视觉/交互缺口。

在同一内容、实际页面 shell 和数据密度下比较有意义的结构方案。用户要多方案时可用 URL variant 与可发现的切换器，使刷新/分享仍能复现；保持原鉴权和数据入口，切换仅改变渲染。方案数按问题价值与用户范围决定，不机械凑三份。

切换器应显示当前方案，键盘操作不拦截输入控件、contenteditable 或原页面已拥有的快捷键。窄屏、溢出、焦点、reduced motion 和关键交互要真实检查，不能仅做换色或假按钮。原型代码在生产不可见的条件必须由实际构建/运行配置证明；未知环境先保留隔离位置，不把 query 参数当鉴权。

不套用 Ponytail 的最小路径或复用阶梯裁剪前端；不得减少用户要求的视觉、交互、状态或动效。原型允许暂不做与问题无关的生产完善，不允许删掉正要验证的复杂状态、错误或交互。

## 收口

记录问题、实际执行的场景/环境、观察、选中/拒绝理由与未解决项。事实与用户选择分别写，不把待看文件算用户接受。获准时保留源产物在项目临时区域或任务分支，链接到项目既有 tracker/方案；Git 位置和采用由 joy-git 核对，不强制新建分支或提交。

要落成产品时交 joy-build 重做合适的生产结构，joy-test 建保护，joy-verify 分层验收；原型通过不等于部署或真实服务成功。未采用内容按已确认用途和授权清理，保留唯一恢复入口，不丢并行工作。
