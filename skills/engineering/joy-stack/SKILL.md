# JoyStack

JoyStack 是一套可组合的工程能力，而不是一篇流程说明。用户只需要描述目标；遇到适合的工程任务时，自动选择最少的组成能力。小改动不强行走全套，复杂工作也不依赖外部 Skill 套件才能完成。

## 默认路由

先辨别任务主导面，再自动交给对应模块；同一任务可按顺序使用多个模块：

- 不清楚现状、行为、历史原因或影响范围：[`joy-understand`](../joy-understand/SKILL.md)；
- 目标、边界、术语或验收条件尚未清楚：[`joy-shape`](../joy-shape/SKILL.md)；
- 实现一个已经清楚的改变：[`joy-build`](../joy-build/SKILL.md)；
- 需要证明交付是否真的成立：[`joy-verify`](../joy-verify/SKILL.md)；
- 复现、定位和修复异常：[`joy-debug`](../joy-debug/SKILL.md)；
- 在合入或交付前检查遗漏：[`joy-review`](../joy-review/SKILL.md)；
- 阶段性治理文档、测试、确定性检查、分支或 worktree：[`joy-govern`](../joy-govern/SKILL.md)；
- 在 Git 仓库安全提交、推送或收尾：[`joy-git`](../joy-git/SKILL.md)；
- 跨轮续接、交接或保留经确认的判断：[`joy-continue`](../joy-continue/SKILL.md)。

现有领域 Skill 优先主导自身职责，例如产品架构、UI、测试质量、写作或目标平台操作。JoyStack 只在它们之间维持同一个目标、边界与证据标准；`joy-git` 只在项目规则与验证证据已明确时负责 Git 交付，不接管发布权限。

## 统一交付契约

无论启用哪个模块，都使用同一份轻量契约：结果、边界、事实、证据与续接。信息足以安全推进时直接做；只有缺少的选择会改变结果、成本、外部影响或不可逆性时才要求用户决定。

## 按风险升级，而非默认重流程

普通任务走“理解最小边界 → 改动 → 贴近风险的验证 → 交付”。明确小改直接推进，常规需求在对话中对齐，跨系统或高风险改造才落规格并增加独立检查。出现跨系统状态、数据兼容、权限/付费、外部发布、关键事实不确定或无法本地证明的成功条件时，再额外检查价值、恢复和证据三件事。详细协作边界与未来能力接入方式见[套件契约](references/stack-contract.md)。

## 可演进，而不锁定上游

JoyStack 吸收可公开、可验证的工程思想，但不要求安装任何特定第三方技能。以后发现更好的套件时，按套件契约为它标注覆盖的能力与输入/输出，即可替换或补强单个模块；不复制上游文本、脚本、资产或运行时，也不让一个总控流程垄断专业判断。已完成的上游映射见[融合记录](references/oil-dev-integration.md)。

## 交付

先说明结果，再区分实际运行过的验证、尚未验证的边界，以及确有必要的下一步。代码、测试、构建、提交、推送、部署和真实业务结果是不同证据，不能互相替代。
