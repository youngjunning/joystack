# JoyStack

跨技能交接按名称使用当前宿主已发现的 Skill，不要求相邻安装目录；缺少所需能力时报告缺项，不猜路径或擅自安装。

JoyStack 是一套可组合的工程能力，而不是一篇流程说明。用户只需要描述目标；遇到适合的工程任务时，自动选择最少的组成能力。小改动不强行走全套，复杂工作也不依赖外部 Skill 套件才能完成。

## 默认路由

先辨别任务主导面，再自动交给对应模块；同一任务可按顺序使用多个模块：

- 不清楚现状、行为、历史原因或影响范围：`joy-understand`；
- 目标、边界、术语或验收条件尚未清楚：`joy-shape`；
- 领域建模、模块接口或原型需要决定：`joy-shape` 的对应按需分支；一手资料待查交 `joy-understand`；
- 实现一个已经清楚的改变：`joy-build`；
- 测试策略、TDD、用例实现与运行、测试失败或 AI/Agent evals：`joy-test`；
- 需要证明交付是否真的成立：`joy-verify`；
- 复现、定位和修复异常：`joy-debug`；
- 在合入或交付前检查遗漏：`joy-review`；
- 实质行为改动需要独立评审、修正与复验闭环：`joy-loop`；
- 阶段性治理文档、测试、确定性检查、分支或 worktree：`joy-govern`；
- 安全提交、推送或通过分支/PR 合入，以及 worktree 创建、用途盘点、续接与清理：`joy-git`；
- 跨轮续接、交接或保留经确认的判断：`joy-continue`。

工程任务默认由 `joy-token` 提供模型与宿主无关的轻量节流：定向读取、工具侧筛选、复用有效证据与紧凑交接；明确要求省 Token 或出现大量上下文/重复调用时，加载该模块与相关场景细则。它贯穿上述模块，缓存/推理控制/计量只按实际接口能力启用；不另开优化阶段、不默认换模型，也不降低权限、验证或独立评审要求。简单自包含回答不为节流加载全套。

接手或恢复旧变更时，先由 `joy-continue` 核对目标、最新纠正、当前价值与继承贡献，不是先机械 rebase。PR/MR 观察和交付由 `joy-git` 维护终点与真实门禁；评审预算由 `joy-loop` 维护，不因平台或模型切换扩大授权。

现有领域 Skill 优先主导自身职责，例如产品架构、UI、测试质量、写作或目标平台操作。JoyStack 只在它们之间维持同一个目标、边界与证据标准；`joy-git` 按需管理 worktree，并在项目规则与验证证据已明确时负责 Git 交付，不接管发布权限。

测试工作由 joy-test 主导，joy-build 负责产品实现，joy-verify 汇总测试与构建、部署、目标环境的交付证据。只按风险读取测试分支；活动 joy-loop 中仍交回同一 Loop。缺少 joy-test 时报告缺项，只在已有工具足以覆盖当前任务时取得限定证据，不自动安装、不伪造测试通过。

## 全局运行数据

JoyStack 持久运行数据默认在当前环境家目录下的 `.joystack`；家目录由环境解析，不从工作区推断。worktrees 与状态台账统一归入其子目录；安装入口保持用户既有约定。受限平台的路径边界、模块加载与动作授权按 [全局目录与平台适配](references/global-home.md) 处理，安装不扩大平台权限。

## 统一交付契约

无论启用哪个模块，都使用同一份轻量契约：结果、边界、事实、证据与续接。信息足以安全推进时直接做；只有缺少的选择会改变结果、成本、外部影响或不可逆性时才要求用户决定。

## 按风险升级，而非默认重流程

普通任务走“理解最小边界 → 改动 → 贴近风险的验证 → 交付”。明确小改直接推进；实质行为改动在初步验证后由 `joy-loop` 用独立 reviewer 收敛，纯文案和机械改名不增加循环。跨系统或高风险改造才落规格并提高评审与验证深度。出现跨系统状态、数据兼容、权限/付费、外部发布、关键事实不确定或无法本地证明的成功条件时，再额外检查价值、恢复和证据三件事。详细协作边界与未来能力接入方式见[套件契约](references/stack-contract.md)。

## 可演进，而不锁定上游

Matt Pocock Skills、pstack、tstack 与 oil dev skills 的独立来源、方法映射和验证边界统一见[融合记录索引](references/integration-sources.md)。来源对应不等于整体移植或新增运行依赖，未记录的最初参考版本保持未知。

2026-11-24 的[方法补强与入口收敛](references/matt-method-completion.md)记录双轴评审、可运行诊断、领域/模块设计、逻辑/UI 原型、研究与架构体检的当前落点。只读所需分支，不另装被接替的独立入口；仍保留的手动专项不自动视为已替代。

oil dev skills 只作方法来源；执行始终由 JoyStack 与宿主现有工具负责，不安装或调用该套件。具体映射与来源归属见[融合记录](references/oil-dev-integration.md)。

JoyStack 吸收可公开、可验证的工程思想，但不要求安装任何特定第三方技能。以后发现更好的套件时，按套件契约为它标注覆盖的能力与输入/输出，即可替换或补强单个模块；不复制上游文本、脚本、资产或运行时，也不让一个总控流程垄断专业判断。已完成的上游映射见[融合记录](references/oil-dev-integration.md)。

## 交付

已吸收的 tstack 方法与未引入的运行时边界见[融合记录](references/tstack-integration.md)。它补强既有模块，不增加 send/stop 总控或默认多模型调用。

先说明结果，再区分实际运行过的验证、尚未验证的边界，以及确有必要的下一步。代码、测试、构建、提交、推送、部署和真实业务结果是不同证据，不能互相替代。
