# JoyStack 套件契约

JoyStack 的模块以能力边界协作，不以固定顺序或特定模型协作。每个模块都应说明：何时进入、需要哪些事实、产出什么可核对结论、哪些动作不属于它，以及如何把未决项交给下一个模块。

## 共同不变量

- 用户决定、当前事实、方案判断与待验证项必须分开；历史记录不能冒充实时状态。
- 只在风险需要时增加过程。短小、可逆的变更不要求规格会、角色扮演或多 Agent 编排。
- 每项“完成”主张应有相称证据。测试、构建、部署和真实业务结果分别报告。
- 权限、不可逆动作和外部写入仍由项目规则与用户授权决定；协调能力不产生新授权。
- 自己执行、宿主子 Agent 或外部 CLI 都只能作为执行适配器；委托契约必须保留目标、范围、验证和停止条件，返回结果仍需由当前任务回验。
- 模块可以提出候选，不自动把会话、推测或敏感资料写入长期记录。
- 每个模块在 `SKILL.md` frontmatter 中保留作者姓名与联系邮箱，来源身份由仓库校验统一检查。

全局运行数据按 [全局目录与平台适配](global-home.md) 放在环境解析的家目录下 `.joystack`；模块共享根目录与权威台账。受限平台显式提供路径边界，不能把 cwd 当家目录或让安装、自动交付规则扩大平台权限。

## 模块接口

按技能名使用当前宿主已发现的模块；名称标识一份能力与指令，不假定存在同名 API、CLI 或工具。宿主独立挂载各模块时也使用同一契约：

- **发现与加载。** 从当前宿主 Skill 清单解析准确名称，使用它提供的加载方式和实际入口。跨技能引用不拼接兄弟目录；Skill 自己的 `references/`、`scripts/` 和资产才按该入口目录解析。
- **交接。** 传递任务目标、改动范围、权限、证据和停止条件；已在活动 Loop 中的模块把结果交回同一 Loop。名称调用不扩大任务，也不授予子 Agent、Git 或外部动作权限。
- **缺项。** 缺少所需模块或配套文件时，明确区分“未安装/未发现”“加载失败”“执行权限不足”。只在已有能力足以覆盖当前任务时降级，不伪造验证或独立评审；必需门禁缺失时保留现场和恢复条件，不擅自安装、复制或改写其他模块。
- **授权。** 平台执行权限是上限，用户与项目协议在其内决定动作。已获授权的自动交付正常继续；平台阻止或未授权的提交、推送、合并、删除不执行，不把安装或可读文档当动作许可。

| 能力 | 输入 | 可交接的输出 |
| --- | --- | --- |
| Understand | 现象、代码、资料、历史线索 | 当前行为、未知项、影响范围与来源 |
| Shape | 目标与已知约束 | 最小结果、边界、验收条件与待决定项 |
| Build | 可实现的切片 | 改动、局部反馈与未解决风险 |
| Verify | 主张与风险 | 已执行证据、覆盖盲点与目标环境待验项 |
| Debug | 可观察异常 | 已复现事实、已排除假设、根因与回归保护 |
| Review | 变更与原目标 | 范围/契约/维护性问题及证据 |
| Loop | 已初步验证的任务 diff、独立评审结论与轮次预算 | finding ledger、最新验证证据，以及当前 diff 的 APPROVE 或有证据的 BLOCKED |
| Govern | 仓库文档、测试、规则与 Git 卫生事实 | 分级治理清单、确定性检查候选；worktree 管理交给 Git Delivery |
| Git Delivery & Worktrees | 任务改动、验证证据、项目交付规则或 worktree 管理请求 | Git 交付与提交/远端/PR 证据；位置、任务用途、状态、保留原因、清理条件和实际处置结果 |
| Continue | 已确认状态 | 可续接摘要、仍有效的决定与下一步条件 |

### 继承、评审与变更交付增量

Continue 拥有 `references/inherited-work.md` 的 KEEP/REWORK/SUPERSEDED/UNRESOLVED 与贡献契约，Understand 还原现状，Shape 收敛实质变化，Git 只执行获准的重放/交付。历史 handoff 或无冲突不代替当前验收。

Loop 拥有 `references/review-lifecycle.md` 的 checkpoint、时间/轮次预算、终止确认与 diff-growth；Review 提供基于证据的 finding，多视角按权限可选。预算耗尽、评分或仅打印 verdict 不替代终态。

Git 拥有 `references/pr-delivery.md` 与 `references/pr-observation.md` 的 PR/MR 终点、贡献、评论与单一观察所有者；观察只返回事件和完整性，不产生 merge 授权。领域适配器在自身范围内映射同一语义，核心不绑定供应商或私有 API。

以上 references 均从所属 Skill 的实际目录解析，不要求兄弟安装。缺少平台/多模型/通知能力时保留缺项，普通工程与获准直接 Git 交付仍可运行。

`Loop` 是组合控制能力，不重复其他模块的专业判断：`Review` 定义 finding，`Build` 完成经核实的最小修正，`Verify` 更新证据，`Loop` 只维护轮次、ledger 与停止条件。一次只读评审可以直接使用 `Review`；需要作者修正并复验到可信终态时进入 `Loop`；通过后再由 `Git Delivery` 按项目规则选择直接提交推送或分支/PR 合入。

`Git Delivery` 同时拥有 worktree 生命周期（按技能名发现 `joy-git`，再从其实际目录读取 `references/worktrees.md`）：隔离开始时进入，不等到交付。Govern 只发现治理需要，不另建台账或清理规则。worktree 查询不修改 Git；本机登记不制造仓库提交；清理候选不授权删除，也不依赖特定宿主或第三方管理器。

## 融合后续套件

引入任何新能力前，先为它建立一张能力卡：触发场景、负责的输出、依赖事实、验证方式、权限边界与来源/许可。再映射到上表的一个或多个能力：

1. 若它给出更好的实现方式但拥有同一输入/输出，替换对应模块，不让两个模块重复发号施令；
2. 若它覆盖新能力，新增独立模块，并把交接条件写回本表；
3. 若它要求专有 runtime、模型路由、后台服务或账号，保持为可选适配器，不让 JoyStack 的基本能力依赖它；
4. 只在许可证允许的范围内复用文本、脚本与资产；一般情况下保留思路、用自己的话与验证重写。

一次融合应至少验证：原有任务仍能完成、新模块在它的触发场景能产出可观察结果、以及安装该模块与不安装它时的降级行为都明确。

当前已完成的 oil dev skills 能力卡、映射和保留边界见 [oil dev skills 融合记录](oil-dev-integration.md)。

tstack 九个 Skill 的映射、静态契约案例与运行验收边界见 [tstack 融合记录](tstack-integration.md)。
