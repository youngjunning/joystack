# 测试质量审查

在用户要求评估 AI 生成测试、审查 PR 测试、缩短慢套件、处理不稳定测试或系统治理测试资产时使用本参考。先限定范围并读取测试的真实运行入口；全仓审查应分组抽样或分批完成，说明覆盖范围与未检查部分。

## 判断每组测试

1. 写出它声称保护的行为和断言实际观察到的结果，核对预期是否独立来自需求或协议。
2. 给出一个具体、可信且有影响的回归，判断该回归发生时测试是否会失败，以及行为仍正确但内部重构时是否会误报。
3. 检查相邻测试是否覆盖同一失败机制，或是否存在不同边界与失败路径使它们都有独特价值。
4. 检查 mock 是否替换了应验证的行为，快照是否能被语义审阅，fixture 是否把预期和实现绑定成同一份数据。
5. 核对测试是否真正进入常用验证命令，并记录耗时、非确定性、数据准备、内部耦合和失败定位成本。没有实测就保留未知。

当重要结论取决于测试对某个缺陷是否敏感时，优先使用失败前证据或已知坏版本。必要的临时缺陷实验放在隔离副本中，保持被审查测试不变；只报告所试缺陷的结果，不把一次实验外推为全面保证。

## 处置

| 结论 | 依据与动作 |
| --- | --- |
| 保留 | 能观察有意义的契约，可信回归会使其失败；即使涉及内部细节，也有独特保护价值。 |
| 改写 | 保护目标有价值，但断言、mock、fixture 或运行方式导致漏报、误报或无法执行；改为观察实际行为。 |
| 删除 | 没有独立保护价值，或维护代价明显高于所保护风险且不值得改写；先核对兼容承诺及替代证据。 |
| 补充 | 关键契约存在可信回归风险而现有测试未覆盖；只补最小且可稳定运行的场景。 |
| 隔离 | 当前非确定性会污染必要门槛，且暂时无法完成修复；保留可见性、解除条件和剩余风险。 |

仅检查文件、常量、选项或函数调用是否存在的测试，先确认这些是否属于对外承诺；不要仅因形式删除。静态文案、原型和已移除功能通常不需新增回归测试，除非存在兼容、安全或合规承诺。

对改动过的测试，比较前后实际能挡住的缺陷。删除旧断言前确认契约已变更、旧断言错误，或替代测试仍挡住同一风险。接口重命名不自动意味着原来的失败场景可以丢失。

## 交付审查结论

按影响排序说明每组测试的保护契约、具体回归、判断证据与处置建议。证据不足时给出最小核对动作。优先提出能提高缺陷发现率、减少误报或降低稳定成本的少量改动，不为填满分类而凑建议。

用户要求实际治理时，先保留有价值的保护，再做最小修改并运行受影响验证。若暴露产品缺陷，保留失败并报告；测试清理不授权悄悄削弱断言或扩大为产品代码修复。
