# 非确定性系统评测

用于 LLM 输出、RAG、工具调用、多步 Agent、Agent Skill 或其他相同输入可能产生不同结果的系统。单次成功不能证明稳定性；先固定任务、样本、环境和评分方式，再比较版本。

## 定义评测契约

1. 写清最终目标状态、不可违反的约束、关键失败类型，以及延迟、成本或工具权限等次要指标。
2. 建立带来源和切片标签的 case 集：覆盖真实常见请求、高影响边界、已知失败和拒绝路径；合成样本明确标注。开发集与冻结回归集分开，避免调 prompt 时把评测答案学进去。
3. 优先使用可确定验证的结果：文件或外部状态、schema、精确字段、工具副作用、安全约束。只有语义质量无法确定判断时才引入人工或模型 grader。
4. 为每个 case 规定成功条件和严重性。关键 case 的失败不能被大量低风险通过率平均掉。

## 运行与比较

涉及退款、支付、删除、发信、发布或其他高影响写工具时，默认使用 stub、dry-run、回放或隔离测试环境，并验证原生产状态未被改变。只有用户明确授权真实写入、目标可恢复且保护措施已核对时，才在真实服务执行对应 eval；评测需求本身不构成这种授权。

候选与基线使用相同 case、工具版本、环境和预算配对运行。随机系统对每个 case 预先规定重复次数并保留每次结果，不在看到失败后临时追加重跑。区分“多次中至少一次成功”的能力信号与“连续多次都成功”的可靠性信号，并报告分母、失败分布和切片差异。

对 Agent 同时验证最终外部状态与必要轨迹约束。只有当工具选择、禁止工具、顺序或审批属于契约时才给轨迹打分；不要因一条不同但有效的路径判错。多步任务检查中间状态、恢复和幂等性，因为最终文本可能掩盖早期副作用。

比较 prompt、模型、Skill 或 runtime 版本时保留基线，不只看候选的绝对分数。样本或重复次数不足以区分波动与回归时给出不确定结论，不把小样本变化包装成提升。

## Grader 与门槛

评分梯度依次为：确定性检查、规则或参考答案、经校准的人工 rubric、模型 grader。LLM-as-judge 使用明确维度和可引用证据，并用人工标注样本检查一致性、偏差和版本漂移；grader 的输出是一个测量，不是客观真值。

发布门槛同时包含关键 case 下限、总体或切片相对基线、不可违反约束和资源预算。失败时保留原始 case、运行版本、输出、工具轨迹和 grader 理由；先判断是产品回归、case 错误、grader 漂移还是环境差异，再决定修复哪一层。
