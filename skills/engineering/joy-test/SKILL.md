# JoyStack · Test

用最小而可信的证据保护产品行为。测试数量、覆盖率、快照规模和写作顺序不能单独证明价值；先找需要保护的契约与可信回归，再决定测试层级、oracle、运行范围和治理动作。

## 主栈职责与交接

joy-test 是测试工作的主入口，负责测试策略、用例与 harness、测试执行、失败分类、质量治理和 AI/Agent evals。跨技能按当前宿主发现的准确名称加载，不拼接兄弟目录；本 Skill 的 references 从自己的安装目录解析。

- joy-build 负责产品实现；测试设计、test-first 和回归保护由 joy-test 承接。明确要求 test-first 或 TDD 时，先沿已有需求与接口确认测试 seam 和独立 oracle，再执行红灯 → 最小实现 → 绿灯；已有契约足够时不重复要求用户确认。
- joy-verify 汇总整个交付的证据与未覆盖门禁；joy-test 返回测试范围、命令、环境和观察结果，不把测试通过提升为完整交付通过。
- 测试错误和不稳定测试由 joy-test 定位；机制不明的产品缺陷交给 joy-debug。测试治理不自动授权产品修复，原任务已授权时沿用同一范围。
- joy-govern 发现仓库级测试卫生问题后，把具体测试保护价值与处置交给 joy-test；主栈源码审查仍由 joy-review 主导。
- 活动 joy-loop 调用本模块时，只回传最新测试证据与风险，不启动第二个 Loop，也不重置评审预算。没有活动 Loop 的测试专项按原目标完成，不强制走全部工程阶段。

## 选择任务分支

先固定用户指定的改动、缺陷、PR、目录、测试组或时间范围，再只加载本次需要的分支：

1. **策略与测试实现**：识别高风险契约，选择单元、集成、契约、端到端、设备或人工验收；需要 test-first、性质测试、fuzz、覆盖率诊断或 mutation 时读取[测试方法](references/test-methods.md)。
2. **目标环境验证**：测试浏览器动态页面、关键 E2E 旅程、API 契约或屏幕阅读器时读取[目标环境测试](references/target-environments.md)。
3. **AI/Agent evals**：评测 LLM 输出、RAG、工具调用或多步 Agent，并比较 prompt、模型、Skill 或运行时版本时读取[非确定性系统评测](references/ai-agent-evals.md)。
4. **执行与失败诊断**：从受影响测试开始；需要根据分支或工作区差异安全缩小运行范围时读取[受影响测试选择](references/affected-tests.md)。区分产品回归、测试错误、环境问题和非确定性失败，再按传播范围扩大验证。
5. **质量治理**：评审测试保护价值，处理重复、过度 mock、脆弱快照、慢测、不稳定测试和套件膨胀；进行系统审查时读取[测试质量审查](references/quality-audit.md)。

不要因为任务涉及代码就自动补齐所有分支。用户只要求审查时默认给结论，不修改测试；用户要求实现、修复或治理时才改动对应范围。测试任务本身不扩大为产品代码修复、发布或外部环境变更；若原任务已经授权这些动作，仍按原范围执行。

## 建立保护目标

读取相关实现、公开接口、调用方、验收标准或缺陷、现有同类测试、fixtures、mocks，以及项目真实使用的验证命令。写清四件事：

1. 需要保护的可观察行为、目标状态或调用方契约；
2. 一个具体、可信且有影响的回归；
3. 独立于当前实现的 oracle 或判定依据；
4. 哪种最小证据能让该回归出现时可靠地变红。

需求没有定义可观察结果时，先补清验收标准或明确做 characterization test；不能从现有输出反推“正确”再用同一输出证明实现。按失败概率、影响、可恢复性和暴露面分配测试投入，不把所有路径等权处理。

测试 seam 或状态所有者本身不清楚时，按名称交 joy-shape 的领域/模块设计分支确认接口与实际调用模式，不依赖已移除的独立 Matt 技能。重构迁移保护时逐项核对契约，不因内部结构改变就删除旧测试。

优先选择最靠近行为、又能穿过真实失败机制的层级。纯规则通常适合单元或性质测试；跨模块协议、序列化、存储或网络边界需要集成或契约测试；只有浏览器、设备、权限、生命周期或完整用户旅程才能暴露的问题才提升到端到端或目标环境验收。低层测试无法证明高层链路，高层通过也不能替代关键规则的精确定位。

## 设计可靠信号

让预期值独立来自需求、协议、可信参考实现或已确认的行为，不照搬生产公式和 fixture 自身。断言优先观察输出、状态、持久化结果、错误语义和真实边界；调用次数、顺序、权限拒绝、数据格式和配置仅在属于契约时断言。

每个测试聚焦一个失败机制，并包含理解失败所需的最少上下文。覆盖主路径时同时检查本次风险真正涉及的边界、失败路径或恢复行为；不按模板机械补齐组合。mock 只隔离不属于当前目标的昂贵或不稳定边界，不替换本应验证的核心行为。快照须有稳定语义和可审阅差异，不能用大快照代替关键断言。

新回归测试优先取得失败前证据：在修复前、已知坏版本或隔离的临时缺陷实验中确认它因目标行为缺失而失败。无法安全取得红灯证据时，明确替代依据。实验不得污染被验证的工作区或削弱原断言。

## 执行与诊断

先确认测试是否进入 CI、提交门槛或团队实际使用的命令，以及 skip、筛选条件、并发、所需环境和外部依赖。按以下顺序扩大验证范围，任一层失败时先定位，不用更大范围掩盖信号：

1. 新增或直接受影响的测试；
2. 同一模块、契约或调用链的相邻测试；
3. 项目规定的构建、静态检查和完整测试门槛；
4. 只有目标风险需要时才执行联网、浏览器、设备、真实服务或统计评测。

失败时先稳定复现并保留首个有信息量的错误，再最小化输入和运行范围。核对失败是否来自产品行为、错误预期、fixture 污染、共享状态、时序、资源泄漏、环境差异、依赖漂移或随机性。重复运行通过只能说明失败可能不稳定，不能证明问题消失；修复后要验证原失败机制已被覆盖，而不是只让当前输出变绿。

若改正测试后暴露产品缺陷，保留失败并报告；没有产品修复授权时不靠放宽断言、增加重试或跳过测试制造通过。需要隔离不稳定测试时，说明受影响门槛、临时保护、负责人或解除条件；隔离不是修复完成。

## 交付证据

分别报告通过、失败、跳过和未运行的范围，并说明每项证据能证明什么、不能证明什么。记录命令、版本、环境、样本或 seed、相关制品和首个失败；只有本次实际观察到的结果才算验证证据。测试通过不等于构建、部署、目标环境或真实业务结果已通过。

治理时同时考虑保护范围、误报、执行概率、定位清晰度和维护成本。没有测量时不声称节省了执行时间；只抽样审查时不把样本结论外推为全仓结论。维护或复核本技能来源时读取[10 个 AI Native 测试 Skill 来源复核](references/source-review.md)。

本技能原有质量治理分支参考 [Marcello Curto 的 Test Quality Audit](https://github.com/marcellocurto/skills/tree/main/skills/test-quality-audit)；扩展能力融合 10 个公开 Agent Skill 的差异化机制。原有流程独立编写并迁入 JoyStack，许可、来源与迁移基线见随包的[来源复核](references/source-review.md)，独立安装不依赖外层仓库文件。
