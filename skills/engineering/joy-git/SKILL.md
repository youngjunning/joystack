# JoyStack · Git Delivery

当任务在 Git 仓库产生实现、修复、测试、文档、依赖或版本改动时，在交付前负责 Git 安全边界。它不替代实现、测试、评审、发布或合并冲突处理；这些能力分别提供改动、验证证据和项目规则。

## 何时进入与交接

在 [`joy-verify`](../joy-verify/SKILL.md) 已给出相称证据，或用户明确要求 commit、push、Git 收尾时进入。输入是任务边界、项目协议、验证结果与当前仓库状态；输出是明确的 Git 交付结果、提交/远端证据和保留在工作区的事项。无本任务改动的只读工作直接返回 `no-action`。

项目 `AGENTS.md`、发布协议和用户当次要求优先于本模块。它们决定作者身份、默认交付方式及 push 是否具有发布副作用；本模块不猜测这些规则，也不把 Git 操作当作发布或业务验收。

## 建立安全边界

在编辑前和提交前分别核对仓库根目录、分支或 HEAD、远端/upstream、作者身份，以及 staged、unstaged 和 untracked 状态。多个仓库、submodule 或 worktree 分别判断。

把文件分为本任务改动、已有并行改动，以及缓存/凭据/日志等不应提交的文件。只可显式暂存已确认属于本任务的文件。若 index 中已有无法确认归属的 staged 改动，或任务改动与并行改动无法可靠拆分，保持现场，不能借助 `git add .`、重排 index、stash、还原或删除来取得“干净”状态。

## 决策与执行

先确认验证与项目规则相称，再选择一个结果：

| 结果 | 适用条件 | 动作 |
| --- | --- | --- |
| `commit-and-push` | 任务改动、验证、作者、目标 ref 和普通 push 的安全门都明确 | 只提交任务文件，普通推送并回读远端 ref |
| `commit-only` | 本地提交安全，但 push 会触发未获授权的发布、迁移或其他高影响动作 | 创建本地提交并报告未推送原因 |
| `leave-uncommitted` | 用户要求保留、验证未完成、关键检查失败或任务边界不能安全拆分 | 不改变 index 或历史，说明位置与恢复条件 |
| `no-action` | 无本任务改动，或请求本来就是只读工作 | 不制造空提交，也不推送他人的提交 |
| `ask` | 需要 force push、删除远端、处理受保护分支/分叉、确定身份或决定无法隔离的高影响动作 | 明确对象、风险和需要用户决定的事项 |

自动推送只允许正常 fast-forward 到已确认的 upstream；不能绕过认证、签名、分支保护或 required checks。提交前检查 staged diff 与项目等价检查；提交后核对提交文件与作者；推送后确认远端 ref 包含该提交。网络、认证或保护规则失败时保留成果并报告恢复入口，不改写历史或改变策略重试。

## 交付边界

交付时独立呈现仓库与当前分支（detached HEAD 显示短 SHA），再区分任务提交、工作区状态、推送状态，以及是否实际发生部署、发布或业务验收。测试、提交、推送、CI 触发、部署和真实业务结果分别是不同证据，不能互相代替。

维护本模块时，用[行为检查](references/behavior-checks.md)演练决策边界；它用于检查判断，不是固定命令模板。
